# Decisions

Each entry gives the decision, the reason and the date. Dependencies are recorded in §2 when they are added to `Cargo.toml`. The candidates in §3 were verified on 2026-10-08 and are rechecked when each one is added.

| D-035 | 2026-10-10 | Running-executable identity (spike S2) comes from direct OS APIs in `kipple-platform`, not `sysinfo`. Linux: `readlink` and `stat` on `/proc/<pid>/exe` (std only), giving device, inode and link count of the file actually running. macOS: `proc_listallpids` and `proc_pidpath` for the path; the identity (device, inode, link count) is the vnode behind the process's first file-backed region, via `proc_pidinfo(PROC_PIDREGIONPATHINFO)` (`libc`), and it counts only when that region's path is the path `proc_pidpath` returns. Windows: `K32EnumProcesses`, `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)`, `QueryFullProcessImageNameW`, then volume serial and file index of the image file (`windows-sys`). Every PID gets an explicit outcome: identified, path only, denied, exited, gone, no executable, or other error. Only exited and gone mean "not running", and gone needs positive evidence (`ESRCH`, or the PID's `/proc` entry missing). Path only, denied and other error are unknown. A `/proc` mounted with `hidepid` or `subset` makes the whole inventory partial. **Amended 2026-10-15 (M2b, for D-050):** each record also carries the process's owner and, each read on its own and kept as unknown when the read fails (never as empty), its working directory, its path-like arguments, the absolute paths in its environment and its mapped files, and on Linux its mount namespace, the identity of its root directory and its effective capabilities. The owner is `CurrentUser`, `Root`, `System`, `OtherUser` or `Unknown`, named only when every user ID agrees: on Linux the four of the `Uid:` line of `/proc/<pid>/status` (not the owner of `/proc/<pid>`, which is root for a process that isn't dumpable), against the current user's from `/proc/self/status`; on macOS the real, effective and saved IDs from `proc_pidinfo(PROC_PIDT_SHORTBSDINFO)`, which works for every user's process; on Windows the user SID (`TokenUser`) from one `WTSEnumerateProcessesExW` level 1 listing, with `SYSTEM` only for S-1-5-18. Linux reads `/proc/<pid>/{cwd,cmdline,environ,maps,ns/mnt,root,status}`; macOS `PROC_PIDVNODEPATHINFO`, `KERN_PROCARGS2` and `PROC_PIDREGIONPATHINFO`; Windows reads only the owner in M2, so the rest is recorded as unsupported. Because command lines and environments hold secrets (04 §8a), only argv[0] and arguments with a `/` that aren't URLs, and only the `:`-separated pieces of environment values that start with a single `/`, are kept. The executable identity rules above are unchanged. | `sysinfo` 0.39.6 returns `exe() == None` for a permission error, a zombie and a kernel thread alike (159 of 166 processes on the Linux runner were denied), strips the kernel's ` (deleted)` marker so a binary replaced in place reports the new file at that path, gives no file identity, and lists threads as processes unless told not to. `stat` on a reported path gives the new file's identity after an in-place replacement on Linux and macOS. The direct probes identified that case on all three OSes, stayed unknown where they could not confirm an identity, and took under 17 ms per snapshot. Evidence in §4.1. |
| D-036 | 2026-10-10 | Directory walking and sizing (spike S3) use kipple's own walker in `kipple-platform`: std `read_dir`, metadata from each `DirEntry` (no-follow), and one task per directory on a bounded `rayon` pool. The walker itself never reads ignore files or git config, never skips hidden entries, never follows links, stays on the root's file system, honours the selector's `max_depth`, and prunes artifacts and exclusions before descending. **Amended 2026-10-15 (D-051):** the config's `exclude.paths` prune only the core's project walk, which neither stops at nor descends into an excluded directory and lists it as an `excluded` omission. An integration's own roots, and the walker sizing a finding above an excluded path, still read it; that finding is held as `excluded`. `ignore` and `dua-core` are not used. Supersedes D-014. **Accepted exception:** on macOS at 1M entries it is 17% behind `dua-core`, outside the S3 acceptance rule; the founder kept the walker on 2026-10-10. If macOS misses a scan budget, the platform walker can read bulk metadata (`getattrlistbulk`) itself. | Warm, it was fastest on Linux (1M: 1226 ms; `ignore` 1800, `dua-core` 2220) and Windows (1M: 2334 ms; 3960 and 3853), and cold on Linux (1M: 9949 ms; 10540 and 10643). On Linux and Windows `ignore` came within 10% only in cold runs, and was 44–77% slower warm. It `lstat`s every entry and `stat`s every directory by full path, while std on Linux (glibc) and macOS stats relative to the open directory. On macOS the walker was fastest at 100k and 17% behind `dua-core`'s bulk metadata at 1M. Owning the walker also leaves room for the handle-relative probes of spike S1. Evidence in §4.2. |
| D-037 | 2026-10-10 | kipple's own directories come from the platform's root resolver, not `etcetera`, keeping the D-015 layout: `kipple` under `$XDG_CONFIG_HOME`, `$XDG_DATA_HOME` and `$XDG_CACHE_HOME` on Linux and macOS (defaults under `$HOME`), and `kipple\config`, `kipple\data` under the `RoamingAppData` Known Folder and `kipple\cache` under `LocalAppData` on Windows, read through `SHGetKnownFolderPath`. It also silently ignores a relative `XDG_*` value and uses the default, where 05 §1 requires unknown, and it can't say where a directory came from, which `doctor` reports. The platform resolves the same roots, with their sources, for discovery anyway. |
| D-038 | 2026-10-10 | The platform runner is the one `Command::new` in kipple's crates. So far it runs only `--version` probes for `git`, `paccache` and `journalctl`, with a 2 s deadline, found on absolute `PATH` entries only. | A deadline that can't stop the child bounds nothing: a hung probe would hang `doctor`. | D-039 | 2026-10-10 | Native-backend tests live in test targets named `native` and run only in the `native` nextest profile (`.config/nextest.toml`; the default profile excludes them), through `cargo xtask test-native`, which refuses to run unless `KIPPLE_TEST_DISPOSABLE_HOST=1`. | D-040 | 2026-10-11 | The project license is MIT (supersedes D-034). `LICENSE` holds the text, every crate sets `license.workspace = true`, and `cargo deny` now checks the workspace crates too. | The founder's choice. |
| D-041 | 2026-10-11 | A root whose own path is a link (for example `~/.cache -> /mnt/ssd/cache`) is resolved once, at root resolution. The root then is the directory the link leads to: its identity (device and inode, or volume serial and file index) is recorded and re-checked like any root's (04 §3.4), the report and `kipple doctor` show both the configured path and the resolved one, and everything below it is confined as usual. Only the root's own path is resolved: links below a root are still never followed, a link chain that can't be resolved or leads to something other than a directory stays an omission, and a resolved root that falls inside another root or a protected path is checked like any other root. Built in M1 session 3. Answers Q-roots. | The founder's choice. Moving a cache or data directory to another disk with a link is common, and skipping such a root hides everything under it. Resolving only the root keeps the no-follow rule for every path kipple walks or acts on. |
| D-042 | 2026-10-11 | Process evidence for a release store kipple runs against as a regular user (Q-M4) is scoped to the processes that could be running from that store. Processes of the current user always count, and any unknown one blocks. Processes of other users count only when the store's permissions let that user read it; otherwise they are left out. Processes of root (`uid 0`) and of Windows `SYSTEM` that kipple can't inspect don't block a store in the current user's home or per-user data directories: the plan and `kipple doctor` list them as a partial-inventory notice with the count. An inventory that hides processes without telling their owners (Linux `hidepid` or `subset`, or a process whose owner kipple can't read) stays partial and blocks. A store outside per-user directories needs complete evidence, so in v0.1 it gets advice only (D-009). An integration's descriptor may ask for stricter evidence, never looser. Running kipple elevated (a sudo mode) stays out of v0.1 (D-009, D-025); it belongs to the privileged-helper design planned for 0.5. Built in M4 with release cleanup. | As a regular user Linux denies `/proc/<pid>/exe` for other users' processes (475 of 732 unknown on the founder's machine), so "any unknown blocks" would block every release cleanup. The stores kipple cleans in v0.1 are per-user. Root running a binary out of a user's release store is rare, and the harm is bounded: on Linux and macOS a deleted executable keeps running until it exits, and Windows refuses to delete a running image, which the executor reports. The notice keeps the gap visible instead of hiding it. A sudo run would resolve `$HOME` and file ownership differently and widen what a mistake can touch, so it needs its own reviewed design. |

| D-043 | 2026-10-11 | The name grammar of schema v1 (06 §3) also allows `_`: a component is 1–64 characters from `[A-Za-z0-9._@+-]`, `_`, and in patterns `*` and `?`. A component containing `**` is refused. | The grammar as written could not name `node_modules` or `__pycache__`, the artifacts the v0.1 catalog is built around. `**` would read as a recursive wildcard, which the schema doesn't have. |
| D-044 | 2026-10-11 | `project-artifact` rules are evaluated by one walk per root per scan, in `kipple-core` over the `FsProbe` port (05 §3), sequentially. This refines D-036: the platform walker sizes what is found, and the `max_depth` and pruning D-036 gave it belong to this discovery walk. The walk stops at every candidate artifact of any rule and at every directory a registered integration always owns, by its name or by a file in it such as `pyvenv.cfg`, never descends into either or into a link, and goes as deep as the deepest rule's `max_depth`. A directory it can't list becomes an `Unlisted` omission. An integration's project findings arrive when its walk of that root completes, not one by one during it. `Engine::new` refuses a rule whose integration isn't registered. Generic `dirs-matching` and `files-matching` rules are validated in M1 but evaluated only when third-party packs can be added (M5): no built-in rule uses them, and evaluation without a consumer would be untested code. Rule predicates (`[rule.when]`) and retention are not evaluated before the facts that feed them exist (M3, M4); every built-in rule is `report` in M1. | Walking each root once per integration would multiply the I/O by the number of project integrations, and stopping at artifacts is what keeps nested projects inside `node_modules` or `target` from being reported (05 §3). A rule nobody evaluates would be silently ignored, which reads as "nothing found". Reporting after the walk keeps the walk simple and sequential; the S3 measurement (§4.3) shows it well inside the budget. |
| D-045 | 2026-10-11 | Root facts the platform can't establish stay unknown, never defaulted: an `Include` inside pacman.conf's `[options]` leaves `pacman.cache` unknown (the included file may set `CacheDir`), while a missing `/etc/pacman.conf` means pacman isn't installed and the root is absent. There is no Windows `trash` root in M1: the Recycle Bin has no directory kipple could size without the native backend (M3). A `--root` is placed in the directory its parent names, with the parent's links and `..` resolved (on Windows in the usual `C:\` or `\\server\share` form, so a root given directly and one reached through a link compare equal), so one directory given two ways is one root and no root has a `..` component; its own name is kept, so a `--root` that is itself a link still gets D-041's resolution and identity check, as does a pacman `CacheDir` with `..`; of two roots at the same directory, the one kept carries a link's identity check if either has one, and so shows the link as the configured path. A `--root` that doesn't exist is unresolved rather than absent: the user named it, so finding nothing there must not read as clean. The Linux trash root is the home trash's `files`, where the trashed files are, since `info` and `files` stay after the trash is emptied. Claude Code advice reads only the user `settings.json` under the resolved `claude.config` root and says that managed, project and command-line settings, which it doesn't read, can override it. | Unknown means blocked (04 §1). Showing a retention value that a higher-precedence setting overrides would be wrong advice; saying which sources were read keeps it honest. |
| D-046 | 2026-10-11 | `cargo xtask verify-demo` is the M1 end-to-end check. | D-047 | 2026-10-11 | Buckets (04 §2a) are a pure `kipple-core` function (`classify(&Facts, Level)`, since D-051 `Policy::verdict`), over facts the engine establishes when it measures a finding (05 §2, Buckets). Careful, Balanced and Thorough follow 04 §2a's table; the frontends used Balanced until D-051 made the level configurable. **Git:** `.git` (a file, link or directory) is looked for in the finding and in every directory above it through the `FsProbe`, and the walker that sizes the finding reports any `.git` entry inside it. Nothing is tracked only when none was found anywhere and every directory above was checked and the walk read every entry. An enclosing repository, a directory above that can't be checked, or an incomplete walk leaves `git.tracked_files_in_item` unknown, and a checkout the walk met inside the finding (such as an editable install cloned into a `.venv`) holds it as `holds-repository`, even when the walk was otherwise incomplete, so the finding is Protected until M3 can ask git itself. The walker doesn't enter a directory on another file system (a mount or a btrfs subvolume), so its bytes stay out of the size, which is then a lower bound (`Incomplete`, counting the skipped mounts); the engine treats it like an incomplete walk for git and last change, so the finding is held, and the detail pane names the mount as the reason. **Activity:** one D-035 process snapshot per scan; a process whose executable path lies inside the finding uses it, and any process kipple couldn't identify, or a partial inventory, leaves activity unknown. D-042's scoping is for release stores and arrives with them in M4, so until then project artifacts on a real machine usually stay Protected for unknown activity. The comparison is by path: a finding reached through a linked parent directory could miss a process running it by its other path, which only ever leaves an in-use finding unflagged when every process was identified, and M3 revalidates by file identity before acting. **Last change:** the newest modification time of the finding and everything inside it, directories included, from the walker, against an injected `Clock`; an incomplete measurement, or one that skipped a directory on another file system, leaves it unknown. **Consequences** are set in code by the Cargo, Node and Python integrations for a layout they recognised (06 §5a), and their rules now propose `remove-files` by `delete` or `trash`; whether a method is available and granted is not evaluated until the executor exists (M3), so nothing is removable yet. **Advice** is per integration: once one gives any, each of its report-only findings proposes `advice` (06 §6). With the `test-roots` feature, the test-roots file can fix the clock (`now = <seconds>`) and the process table is empty and complete, so `verify-demo` and the 80% check (04 §2a) are deterministic. | Frontends must agree on a bucket and switch levels without rescanning, which a pure function over stored facts gives. Treating every unproven fact as a hold keeps "unknown means blocked" (04 §3.3) without defaulting anything to idle. |
| D-048 | 2026-10-11 | The home screen (03 §5) is a `tui` module of the `kipple` crate: a state machine (`App::update(Msg)`), a pure renderer and one loop (05 §4). `kipple` without a command opens it when stdout is a terminal and otherwise prints each bucket's total. The loop waits for a key at most one 16 ms frame while the scan runs and 250 ms once it has ended, applies at most 256 scan events between keys, draws at once after a key and at most once a frame otherwise. A finding not yet measured sits under **Measuring**, never in Safe. `c` selects the Safe bucket as it stands at that keypress. With no review screen until M3, `c` and `enter` only say what is selected and that nothing was changed. The filter is a case-insensitive subsequence match over the rule's title and the path, written here rather than taken from `nucleo-matcher`: a few hundred rows don't need ranking. `tab` shows one lens. `NO_COLOR` comes from the environment snapshot (05 §1), and `--ascii` swaps every symbol and border for ASCII. ratatui's `try_init` and `restore` handle raw mode, the alternate screen and the panic hook, with a guard that restores the terminal on every exit. The lens-first variant is the same state machine with `Layout::Lenses`, behind the hidden `--layout lenses` flag until the founder picks one. `cargo xtask bench-tui` runs the same loop on a 160×48 `TestBackend` over the 1M `bench-tree` tree, with the project markers its hot spots lack added, while a thread presses a key every 16 ms from the first frame on. A key counts from when it was pressed to the next flush after the loop read it, and only if it was pressed while a scan ran; the tree is scanned again until 200 keys were. ### 4.2 S3: walker and sizing

Reference trees from `cargo xtask bench-tree`: 100000 entries (16989 directories, 83011 files, 112278450 bytes) and 1000000 entries (169981 directories, 830019 files, 1102545689 bytes). Every variant counted the same entries and bytes with no errors. Every variant used all CPUs, never followed links, and checked the root's device on Linux and macOS. On Windows none of them follows junctions or mount points, and only `ignore` also checks the volume. Medians are of 5 runs. Peak RSS comes from GNU time on Linux and BSD `time -l` on macOS; there is no wrapper for it on Windows. Syscalls come from `strace -f -c` on one warm Linux run.

| `dua-core` | 1079 | 211 | 10643 | 2220 | 3.1 | 267806 / 2672843 |

| Variant | macOS 100k | macOS 1M | Windows 100k | Windows 1M |
| --- | ---: | ---: | ---: | ---: |
| `read_dir` + `rayon` | **327** (2.2) | 11619 (2.3) | **287** | **2334** |

The macOS runner is noisy. Its 1M samples spread by up to 38% within one variant, for example 10299 to 14234 ms for `ignore`.

Why `ignore` is slower: with `follow_links(false)` it `lstat`s every entry by full path, and `same_file_system(true)` adds a full-path `stat` of every directory. std's `DirEntry::metadata` uses `statx`/`fstatat` relative to the open directory on Linux (glibc) and macOS. Linux musl builds fall back to a full-path `lstat` in std. `dua-core` reads native bulk metadata on macOS (`getattrlistbulk`), which is why it leads there at 1M.
