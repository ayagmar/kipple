| D-035 | 2026-10-10 | Running-executable identity (spike S2) comes from direct OS APIs in `kipple-platform`, not `sysinfo`. Linux: `readlink` and `stat` on `/proc/<pid>/exe` (std only), giving device, inode and link count of the file actually running. macOS: `proc_listallpids` and `proc_pidpath` for the path; the identity (device, inode, link count) is the vnode behind the process's first file-backed region, via `proc_pidinfo(PROC_PIDREGIONPATHINFO)` (`libc`), and it counts only when that region's path is the path `proc_pidpath` returns. Windows: `K32EnumProcesses`, `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)`, `QueryFullProcessImageNameW`, then volume serial and file index of the image file (`windows-sys`). Every PID gets an explicit outcome: identified, path only, denied, exited, gone, no executable, or other error. Only exited and gone mean "not running", and gone needs positive evidence (`ESRCH`, or the PID's `/proc` entry missing). Path only, denied and other error are unknown. A `/proc` mounted with `hidepid` or `subset` makes the whole inventory partial. **Amended 2026-10-15 (M2b, for D-050):** each record also carries the process's owner and, each read on its own and kept as unknown when the read fails (never as empty), its working directory, its path-like arguments, the absolute paths in its environment and its mapped files, and on Linux its mount namespace, the identity of its root directory and its effective capabilities. The owner is `CurrentUser`, `Root`, `System`, `OtherUser` or `Unknown`, named only when every user ID agrees (since D-052 one whose effective ID is root and whose others are root's or the current user's is `Elevated`): on Linux the four of the `Uid:` line of `/proc/<pid>/status` (not the owner of `/proc/<pid>`, which is root for a process that isn't dumpable), against the current user's from `/proc/self/status`; on macOS the real, effective and saved IDs from `proc_pidinfo(PROC_PIDT_SHORTBSDINFO)`, which works for every user's process; on Windows the user SID (`TokenUser`) from one `WTSEnumerateProcessesExW` level 1 listing, with `SYSTEM` only for S-1-5-18. Linux reads `/proc/<pid>/{cwd,cmdline,environ,maps,ns/mnt,root,status}`; macOS `PROC_PIDVNODEPATHINFO`, `KERN_PROCARGS2` and `PROC_PIDREGIONPATHINFO`; Windows reads only the owner in M2, so the rest is recorded as unsupported. Because command lines and environments hold secrets (04 §8a), only argv[0] and arguments with a `/` that aren't URLs (argv[0] whole, so a program path with spaces stays one path, but cut before its first word holding `://`, since a title rewritten into it can hold the whole command line), and only the `:`-separated pieces of environment values that start with a single `/`, are kept. The executable identity rules above are unchanged. **Amended 2026-10-15 (M2b, kernel threads):** a reader who isn't root is refused a kernel thread's `/proc/<pid>/exe` (`EACCES`) like any root process's, so a refused `exe` is checked against the `PF_KTHREAD` bit (0x00200000) of the flags field of `/proc/<pid>/stat`, which anyone can read, counted after the last `)` so a command name can't shift the fields. With the bit set the process has no executable and is left out like an exited one; a `stat` that can't be read or parsed, or flags without the bit, leave it denied. | `sysinfo` 0.39.6 returns `exe() == None` for a permission error, a zombie and a kernel thread alike (159 of 166 processes on the Linux runner were denied), strips the kernel's ` (deleted)` marker so a binary replaced in place reports the new file at that path, gives no file identity, and lists threads as processes unless told not to. `stat` on a reported path gives the new file's identity after an in-place replacement on Linux and macOS. The direct probes identified that case on all three OSes, stayed unknown where they could not confirm an identity, and took under 17 ms per snapshot. Evidence in §4.1. |

### 4.1 S2: running-executable identity

Snapshot of every process from the 100k run. "Unknown" is denied, path only or other error.

| OS | Processes | Identified | Unknown | Not running | No executable | Direct probe | `sysinfo` path | `sysinfo` + `stat(path)` |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Linux runner | 166 | 7 | 159 (denied: other users) | 0 | 0 | 0.43 ms | 4.71 ms | 4.75 ms |
| macOS runner | 573 | 314 | 258 (257 path only: region info refused for other users) | 1 | 0 | 7.79 ms | 5.48 ms | 10.14 ms |
| Windows runner | 148 | 144 | 2 (`QueryFullProcessImageNameW` failed with error 31) | 0 | 2 | 16.91 ms | 7.12 ms | 10.50 ms |

Times are medians of 21 snapshots. On Linux, `sysinfo` reported `exe() == None` for all 159 denied processes, which is the same value it gives a zombie or a kernel thread. With `/proc` remounted `hidepid=invisible`, the Linux runner saw 7 processes instead of 166, and no error. Only the mount options in `/proc/self/mountinfo` show that the inventory is partial. On macOS the first mapped file matched `proc_pidpath` for every process whose region info could be read.

### 4.2 S3: walker and sizing

Reference trees from `cargo xtask bench-tree`: 100000 entries (16989 directories, 83011 files, 112278450 bytes) and 1000000 entries (169981 directories, 830019 files, 1102545689 bytes). Every variant counted the same entries and bytes with no errors. Every variant used all CPUs, never followed links, and checked the root's device on Linux and macOS. On Windows none of them follows junctions or mount points, and only `ignore` also checks the volume. Medians are of 5 runs. Peak RSS comes from GNU time on Linux and BSD `time -l` on macOS; there is no wrapper for it on Windows. Syscalls come from `strace -f -c` on one warm Linux run.

Linux runner:

| Variant | 100k cold | 100k warm | 1M cold | 1M warm | Peak RSS 1M warm (MiB) | Syscalls 100k / 1M |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `read_dir` + `rayon` | **1004** | **125** | **9949** | **1226** | 2.8 | 185230 / 1865363 |
| `ignore` (05 §3 settings) | 1061 | 180 | 10540 | 1800 | 4.0 | 202487 / 2024293 |
| `dua-core` | 1079 | 211 | 10643 | 2220 | 3.1 | 267806 / 2672843 |

macOS and Windows runners, warm (ms, peak RSS in MiB on macOS):

| Variant | macOS 100k | macOS 1M | Windows 100k | Windows 1M |
| --- | ---: | ---: | ---: | ---: |
| `read_dir` + `rayon` | **327** (2.2) | 11619 (2.3) | **287** | **2334** |
| `ignore` | 352 (2.9) | 11548 (3.2) | 509 | 3960 |
| `dua-core` | 376 (2.5) | **9902** (2.9) | 630 | 3853 |

The macOS runner is noisy. Its 1M samples spread by up to 38% within one variant, for example 10299 to 14234 ms for `ignore`.

Why `ignore` is slower: with `follow_links(false)` it `lstat`s every entry by full path, and `same_file_system(true)` adds a full-path `stat` of every directory. std's `DirEntry::metadata` uses `statx`/`fstatat` relative to the open directory on Linux (glibc) and macOS. Linux musl builds fall back to a full-path `lstat` in std. `dua-core` reads native bulk metadata on macOS (`getattrlistbulk`), which is why it leads there at 1M.

### 4.3 S3 budget: known-root findings on the 100k tree

Measured 2026-10-11 on the founder's workstation (AMD Ryzen 9 9950X3D, 32 threads, Arch Linux, Linux 7.2.8; trees on tmpfs `/tmp`), not on CI. A release build of `kipple` with the `test-roots` feature scanned with `KIPPLE_TEST_ROOTS` pointing `config.project-roots` at a 100000-entry `cargo xtask bench-tree` and every other root into `demo-home`. A Python script started `kipple scan --events jsonl` and timestamped each line as it arrived on the pipe: one warm-up run, then the median of 5 warm runs.

| Tree | First known-root finding | First project finding | Scan completed | Findings |
| --- | ---: | ---: | ---: | ---: |
| bench tree as generated (no project markers) | 1.0 ms | — | 9.3 ms | 3 |
| each bench project given a `Cargo.toml` and `package.json` | 1.2 ms | 7.9 ms | 15.3 ms | 36 |

Known-root findings (trash, pacman cache, journal) arrive well under the 250 ms budget. The discovery walk lists only the directories within the rules' `max_depth` (6) that aren't artifacts or `node_modules`, `.venv` and `__pycache__`; what it finds is sized by the platform walker. Project findings arrive only after the walk of their root completes (D-044). The time is for the whole process, start to `completed` record, so it includes start-up and sizing. strace and perf weren't installed, so there are no syscall counts. The 1M tree and the CI runners are left for the M2 `bench-tui` work.
